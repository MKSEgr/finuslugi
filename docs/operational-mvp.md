# Operational MVP v0.1

## 1. Назначение

Operational MVP должен доказать полный путь реальной B2B-заявки:

```text
источник/партнёр
→ подтверждённое намерение клиента
→ квалификация
→ передача допустимому рекламодателю
→ наблюдаемые статусы
→ сверка
→ фактически полученное вознаграждение
→ объяснимое начисление партнёру
```

MVP не является открытой CPA-сетью. Он рассчитан на первые 20–30 заявок, ручную операционную работу и максимум 2–3 рекламодателя.

## 2. Цели

1. Не потерять авторство источника от первого касания до выплаты.
2. Получать согласия до передачи данных.
3. Отделять коммерческое намерение от сырого контакта.
4. Сохранять статусы как append-only события.
5. Различать expected payout, advertiser-approved payout и cash received.
6. Не создавать начисление партнёру без денежного основания.
7. Получать причины отказов, достаточные для улучшения маршрута.
8. Работать даже без API рекламодателя.

## 3. Non-goals

- открытая регистрация веб-мастеров;
- автоматические выплаты;
- ML-скоринг и ML-маршрутизация;
- массовая перепродажа одного лида нескольким компаниям;
- сбор паспортов и полного пакета документов;
- собственное кредитное/лизинговое решение;
- обещание одобрения или конкретных условий;
- сложный SPA и мобильное приложение;
- realtime bidding;
- multi-level affiliate hierarchy.

## 4. Роли

### Клиент

ИП или представитель юридического лица, который сам подтверждает намерение и согласия.

### Distribution partner

Профессиональный участник с существующим клиентским контекстом: продавец коммерческой техники/оборудования, бухгалтер, тендерный специалист, консультант или другой письменно согласованный источник.

### Operator

Сотрудник Finuslugi, который проверяет контактность, коммерческий контекст, полноту данных, дубли и допустимость маршрута.

### Advertiser

Банк, лизинговая, факторинговая или другая финансовая организация, которая принимает решение, ведёт сделку и является источником статусов и вознаграждения.

### Finance/QA

Сотрудник, который проводит сверку, фиксирует денежное основание, начисления, корректировки и споры.

### Administrator

Управляет справочниками и правами, но не может незаметно переписать историю статусов или финансовых событий.

## 5. Два клиентских пути

### Journey A — co-branded self-service

1. Партнёр получает ссылку с `partner_id`, `source_id`, `offer_id` и подписанным attribution token.
2. Клиент самостоятельно открывает co-branded страницу.
3. Страница показывает роль Finuslugi и роль будущего рекламодателя/категории продукта без обещания одобрения.
4. Клиент заполняет минимальную форму.
5. Клиент подтверждает телефон одноразовым кодом или эквивалентным доказуемым способом.
6. Клиент отдельно подтверждает обработку данных и передачу выбранному получателю либо актуальной версии списка получателей.
7. Создаётся `Lead`, immutable attribution snapshot и consent evidence.
8. Operator квалифицирует обращение.
9. Routing rule выбирает одного допустимого рекламодателя.
10. Заявка передаётся вручную, файлом или API.

### Journey B — assisted lead

1. Менеджер партнёра открывает защищённую форму с собственным `partner_id`.
2. Он вводит только минимальный контекст и контакт клиента.
3. Система отправляет клиенту персональную ссылку.
4. До перехода клиента заявка имеет статус `ASSISTED_DRAFT` и не передаётся рекламодателю.
5. Клиент проверяет данные, исправляет ошибки, подтверждает телефон и отдельные согласия.
6. Только после подтверждения создаётся полноценный `Lead`.
7. Дальнейший путь совпадает с Journey A.

Партнёр не может подтвердить согласие за клиента.

## 6. Минимальные поля формы

### Обязательные

- тип клиента: ИП / юридическое лицо;
- ИНН организации или ИП;
- имя контактного лица;
- телефон;
- регион;
- продуктовая потребность;
- примерная стоимость предмета/объём финансирования;
- желаемый срок решения;
- источник и attribution identifiers;
- версия согласий.

### Для первого лизингового клина

- тип имущества;
- новое / с пробегом;
- поставщик или ссылка на предложение, если уже выбран;
- ориентировочный аванс;
- срок существования бизнеса;
- комментарий о текущем этапе покупки.

### Не собирать на первом шаге

- паспорт;
- банковские выписки;
- бухгалтерскую отчётность;
- фотографии документов;
- реквизиты банковских карт;
- документы бенефициаров;
- сведения, не влияющие на квалификацию или маршрутизацию.

## 7. Attribution snapshot

При создании лида фиксируются неизменяемые поля:

```text
partner_id
source_id
offer_id
offer_terms_version_id
click_id
signed_attribution_token
utm_source
utm_medium
utm_campaign
utm_content
utm_term
landing_variant
referrer
first_touch_at
lead_created_at
```

Изменение партнёра после создания лида запрещено. Исправление возможно только через отдельное событие `ATTRIBUTION_DISPUTE_RESOLVED` с основанием, доказательствами и автором.

## 8. Авторство лида

По умолчанию используется `first valid verified lead`:

1. технический дубль одной формы не создаёт новое авторство;
2. неподтверждённый assisted draft не резервирует клиента навсегда;
3. авторство возникает после подтверждения телефона и согласий;
4. окно защиты определяется версией оффера и правилами рекламодателя;
5. другой продукт может создавать отдельную коммерческую потребность;
6. существующий клиент рекламодателя не превращается автоматически в fraud партнёра;
7. спор решается по append-only доказательствам, а не после появления крупной выплаты.

## 9. Дедупликация

### Нормализованные ключи

- телефон;
- ИНН;
- категория продукта;
- advertiser;
- offer terms version;
- временное окно.

### Типы дублей

- `TECHNICAL_DUPLICATE` — повторная отправка формы;
- `SAME_NEED_DUPLICATE` — та же потребность в активном окне;
- `ADVERTISER_EXISTING_CLIENT` — клиент уже существует у рекламодателя;
- `PARTNER_OWNERSHIP_CONFLICT` — конкурирующие источники;
- `NEW_PRODUCT_NEED` — новая допустимая потребность;
- `REAPPLICATION_ALLOWED` — повторное обращение после окончания окна.

Решение дедупликации сохраняет правило, версию, ключи сравнения и результат без записи PII в audit metadata.

## 10. Квалификация

Operator проверяет:

- телефон подтверждён;
- клиент понимает цель обращения;
- организация существует;
- потребность соответствует офферу;
- известны предмет, ориентир суммы и срок;
- нет запрещённой категории или источника;
- нет блокирующего дубля;
- согласия действительны;
- рекламодатель принимает такой профиль.

Результаты:

- `QUALIFIED`;
- `NEEDS_CLARIFICATION`;
- `NOT_QUALIFIED` с кодом причины;
- `DUPLICATE`;
- `CONSENT_INVALID`;
- `SOURCE_NOT_ALLOWED`.

Свободный комментарий не заменяет структурированный reason code.

## 11. Routing v0

Маршрутизация детерминированная.

Порядок:

1. исключить рекламодателей, не разрешающих источник/партнёрскую модель;
2. исключить неподходящие географию, продукт, чек, возраст бизнеса и тип имущества;
3. проверить cap и доступность канала передачи;
4. проверить dedup/существующего клиента;
5. выбрать рекламодателя по заранее утверждённому приоритету;
6. зафиксировать `RoutingDecision` и версию правила;
7. передать только одному рекламодателю.

Повторный маршрут допустим только после структурированного результата, который это разрешает, и при наличии соответствующего согласия клиента.

## 12. SLA

### Finuslugi

- проверка новой заявки в рабочее время: до 30 минут;
- запрос уточнения: до 2 часов;
- передача квалифицированной заявки: до 30 минут после квалификации;
- исправление технической ошибки маршрута: немедленно после обнаружения;
- ответ партнёру по спору: до 2 рабочих дней.

### Advertiser — целевые требования для договора

- подтверждение приёма: до 15 минут через API или до 1 рабочего часа вручную;
- первый контакт с клиентом: до 30 минут в рабочее время;
- первичный структурированный статус: до конца рабочего дня;
- обновление активной сделки: минимум раз в 5 рабочих дней;
- причина отклонения: обязательный reason code;
- реестр выплат: по согласованному календарю.

Если рекламодатель не предоставляет наблюдаемые статусы, он не может быть единственным маршрутом.

## 14. Причины отказа

Минимальный каталог:

- existing advertiser client;
- duplicate within window;
- invalid contact;
- client withdrew;
- insufficient business age;
- unsupported asset/product;
- amount outside policy;
- adverse credit/underwriting decision;
- documents not provided;
- supplier/asset issue;
- no commercial intent;
- source not allowed;
- consent problem;
- advertiser technical error;
- other — только с обязательным пояснением.

Коммерчески чувствительные underwriting-детали могут оставаться у рекламодателя, но платформа должна получить операционно полезную категорию причины.

## 15. Передача рекламодателю

Поддерживаются три режима:

### Manual

Operator создаёт заявку в кабинете рекламодателя и сохраняет внешний идентификатор и время передачи.

### Registry

Формируется защищённый реестр; импорт и статусы сверяются по `lead_id`/external reference.

### API

Используется idempotency key, request/response audit без PII в стандартных логах, retry policy и dead-letter register.

MVP начинается с manual/registry, если они обеспечивают проверяемый результат.

## 16. Резервный маршрут

Повторная передача другому рекламодателю запрещена по умолчанию.

Она разрешается только если одновременно:

- первый рекламодатель вернул допустимый terminal reason;
- договор разрешает новый маршрут;
- dedup policy второго рекламодателя допускает клиента;
- согласие клиента охватывает второго получателя;
- клиент не отозвал обращение;
- решение зафиксировано как новое событие.

## 17. Финансовый путь

```text
ExpectedPayout
→ AdvertiserApprovedPayout
→ ReconciliationRow
→ Invoice
→ CashReceipt
→ DistributableCash
→ PartnerAccrual
→ PartnerPayment
```

### Инварианты

1. `cash received` не равен `expected payout`.
2. Начисление партнёру создаётся из конкретного денежного основания.
3. Одно основание не может быть распределено дважды.
4. Корректировка создаётся отдельной проводкой, а не изменением истории.
5. Партнёр видит формулу, hold и reason code.
6. Ручное исключение требует двухэтапного подтверждения после появления реальных выплат.

## 18. Ручная сверка MVP

Для каждого рекламодателя ведётся реестр:

```text

offer_terms_version

```

Сверка проводится не реже раза в неделю и перед каждым начислением.

## 19. Операционные исключения

### Потерян source_id

- заявка блокируется для начисления;
- создаётся incident;
- источник восстанавливается только по доказательствам;
- причина технической потери исправляется до масштабирования.

### Рекламодатель не обновляет статус

- заявка помечается `STALE` аналитически, без подмены бизнес-статуса;
- отправляется эскалация;
- advertiser SLA учитывается в рейтинге маршрута.

### Клиент отзывает согласие

- дальнейшая передача останавливается;
- рекламодателю направляется предусмотренное уведомление;
- сохраняется минимальное доказательство исполнения отзыва;
- retention/удаление выполняются по утверждённому регламенту.

### Спор партнёра

- партнёр подаёт спор по конкретному lead/outcome;
- фиксируются доказательства;
- статус и деньги не переписываются;
- решение оформляется отдельным событием.

### Ошибка рекламодателя

- ответ и external reference сохраняются;
- повторная отправка использует idempotency key;
- клиент не получает несколько звонков из-за технического retry.

## 20. Pilot mode

Первые 20–30 заявок проходят с ручным контролем каждой стадии.

Обязательные ежедневные проверки:

- новые заявки без владельца;
- неподтверждённые assisted drafts;
- потерянная атрибуция;
- невалидные согласия;
- заявки без advertiser acknowledgement;
- просроченный first contact;
- устаревшие статусы;
- дубли;
- финансовые события без основания.

## 21. Exit criteria operational MVP

Operational MVP считается спроектированным и готовым к реализации, когда:

- оба journey имеют happy path и исключения;
- минимальные поля утверждены;
- consent flow проверен профильным юристом;
- минимум два рекламодателя подтверждают совместимый маршрут;
- dedup window и target event известны;
- статусная модель сопоставлена с реальными статусами рекламодателей;
- ручная сверка может объяснить каждую выплату;
- партнёрское начисление выводится из cash received;
- первые 20–30 заявок можно провести без партнёрского кабинета;
- production-сбор данных не запускается до Gate 0 и compliance approval.
