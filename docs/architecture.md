# Architecture v0.1

## Архитектурное решение

Для MVP используется **модульный монолит**, а не набор микросервисов.

Причины:

- бизнес-правила ещё меняются;
- объём не требует распределённой системы;
- финансовую сверку проще держать в одной транзакционной модели;
- меньше точек отказа и стоимость сопровождения;
- быстрее проверяется экономика;
- код позже можно разделить по фактическим узким местам.

## Предлагаемый стек

- Django monolith;
- PostgreSQL;
- server-rendered интерфейсы для первой версии;
- REST endpoints только для интеграций и будущих партнёров;
- фоновые задачи добавляются после появления реальной асинхронной нагрузки;
- Docker для воспроизводимого запуска;
- CI для тестов, линтинга и проверки миграций;
- российская инфраструктура хранения персональных данных;
- отдельное объектное хранилище для файлов с закрытым доступом.

Точный набор версий фиксируется при создании первого кода и обновляется автоматически только после прохождения тестов.

## Дедупликация

Правила задаются на уровне рекламодателя и версии оффера.

Минимальные ключи:

- нормализованный телефон;
- ИНН клиента;
- продукт;
- advertiser;
- временное окно.

Система должна различать:

- технический дубль одной формы;
- повторную заявку тому же рекламодателю;
- новую потребность по другому продукту;
- существующего клиента рекламодателя;
- спор между двумя партнёрами.

Авторство лида определяется по зафиксированному правилу, а не ручному усмотрению после появления выплаты.

## Интеграции

Поддерживаются три уровня:

1. ручная передача через кабинет рекламодателя;
2. файл/реестр и ручной импорт статусов;
3. API + webhook/postback.

MVP обязан работать на первом уровне, чтобы интеграция не блокировала проверку экономики.

## AI boundary

AI может:

- предложить категорию заявки;
- найти пропущенное поле;
- подготовить оператору вопрос;
- сгруппировать причины отказов;
- выделить аномалию;
- объяснить статус клиенту черновиком.

AI не может без детерминированной проверки:

- изменить авторство лида;
- утвердить начисление;
- выполнить выплату;
- признать fraud;
- дать обещание одобрения;
- отправить чувствительные данные неизвестному получателю.

## Наблюдаемость

Обязательные события:

- потеря source/click_id;
- ошибка передачи рекламодателю;
- отсутствие обновления статуса сверх SLA;
- расхождение реестра;
- попытка двойного начисления;
- изменение условий оффера;
- превышение cap;
- необычная активность партнёра;
- административное изменение финансового события.

## Безопасность

- секреты только в secret store/environment;
- запрет PII в логах;
- минимальные роли и права;
- audit trail административных действий;
- шифрование транспорта;
- резервное копирование;
- регулярная проверка восстановления;
- ограниченный срок хранения лишних данных;
- отдельный production-доступ;
- запрещено использовать production-данные в тестовой среде.
