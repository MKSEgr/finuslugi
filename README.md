# Finuslugi

Evidence-driven партнёрская платформа B2B-финансовых продуктов.

## Зачем существует проект

Рынок партнёрского маркетинга быстро коммодитизируется: одинаковые лендинги, массовый AI-контент, непрозрачные лиды и конкуренция только ставкой. Finuslugi строится не как ещё один каталог офферов и не как контентная ферма.

Цель — создать операционную систему дистрибуции B2B-финансовых решений, в которой:

- рекламодатель получает не «лид», а проверяемый коммерческий результат;
- профессиональный партнёр получает прозрачную атрибуцию, статусы и выплату;
- клиент получает релевантный маршрут, а не массовую передачу заявки;
- решения принимаются по фактически поступившим выплатам, а не по кликам и обещанному CPA;
- собственный трафик используется как контроль качества, а масштаб создают партнёры с существующими клиентскими отношениями.

## Стратегический клин

Первый клин — embedded distribution: продавцы коммерческой техники и оборудования, бухгалтеры, тендерные специалисты, консультанты и другие B2B-профессионалы встраивают финансовые продукты в обычную работу с клиентом.

Это даёт более сильную защиту, чем массовый арбитраж:

1. партнёр уже знает клиента и его реальную потребность;
2. стоимость привлечения ниже холодной рекламы;
3. качество и контактность выше;
4. мотивация партнёра совпадает с результатом клиента;
5. накопленные данные улучшают маршрутизацию и экономику каждого следующего обращения.

## Принципы

1. **Cash truth.** Конверсией считается только результат, подтверждённый рекламодателем и фактически оплаченный.
2. **First-party data.** Мы накапливаем собственные данные о качестве источников, причинах отказов, сроках сделки и фактическом доходе.
3. **No AI slop.** AI используется для ускорения анализа и операций, но не для массового выпуска страниц без новой ценности.
4. **Outcome routing.** Заявка направляется туда, где максимальна ожидаемая вероятность полезного результата для клиента и выплаты для платформы.
5. **Controlled distribution.** Каждый источник трафика объявлен, согласован и измеряется отдельно.
6. **Partner alignment.** Выплата партнёру зависит от полученного платформой дохода, качества и устойчивости его трафика.
7. **Compliance by design.** Согласия, атрибуция, журнал действий, дедупликация и рекламные обязательства проектируются до масштабирования.
8. **Monolith first.** До доказанной экономики используется простая архитектура без преждевременной CPA-платформы.

## Этапы

### Phase 0 — доказательство договорной и экономической реализуемости

- матрица прямых рекламодателей;
- письменное подтверждение разрешённых источников;
- право на собственные посадочные страницы и партнёрскую дистрибуцию;
- точная модель целевых действий, hold, dedup и выплат;
- выбор одного узкого клина.

### Phase 1 — собственный контрольный трафик

- 1–2 продукта;
- один полный путь click → lead → advertiser status → cash received;
- ручная квалификация;
- измерение причин отказа;
- минимум два выплатных цикла.

### Phase 2 — профессиональные партнёры

- уникальные ссылки и формы;
- onboarding и source declaration;
- тестовые caps;
- прозрачный реестр начислений;
- 5–10 активных партнёров вместо сотен регистраций.

### Phase 3 — платформа

- кабинеты партнёра и рекламодателя;
- API/postback;
- автоматическая дедупликация;
- ledger начислений;
- антифрод и quality scoring;
- маршрутизация по ожидаемой ценности.

## Критерии перехода к масштабированию

- минимум два независимых рекламодателя;
- минимум две фактически полученные выплаты;
- полный статусный контур без потери источника;
- известная экономика до уровня cash received;
- разрешение на используемые источники и партнёрскую модель;
- ни один оффер не формирует критическую долю результата;
- качество не основано на одной случайной крупной сделке.

## Технический фундамент

Первая версия — модульный Django-монолит с PostgreSQL. Технические решения и границы модулей описаны в [`docs/architecture.md`](docs/architecture.md).

### Локальный запуск без Docker

Требования: Python 3.13.

```bash
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\Scripts\activate
python -m pip install --upgrade pip
pip install -e ".[dev]"
python manage.py migrate
python manage.py runserver
```

Проверка:

```bash
curl http://127.0.0.1:8000/health/
```

### Локальный запуск с Docker

```bash
cp .env.example .env
# Замените секрет и пароль БД в .env
docker compose up --build
```

Приложение будет доступно на `http://localhost:8000`, health endpoint — на `/health/`.

### Проверки перед PR

```bash
ruff check .
ruff format --check .
python manage.py makemigrations --check --dry-run
python manage.py migrate --noinput
pytest
```

## Репозиторий и конфиденциальность

Репозиторий публичный. Здесь не должны храниться:

- персональные данные клиентов;
- API-ключи и секреты;
- закрытые ставки рекламодателей;
- договоры и коммерческие условия;
- списки партнёров и рекламные связки;
- детальная unit-экономика работающих кампаний.

Такие данные должны находиться в закрытом хранилище и переменных окружения. Production-данные запрещено копировать в локальную или тестовую среду.
